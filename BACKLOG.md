# Бэклог

Идеи и задачи, которые не реализуются прямо сейчас, но планируются или могут понадобиться.

---

## Доступ пользователей к датасетам (`user_dataset_access`)

- **Тип-зависимые квоты**: сейчас есть `labeling_limit`/`labeled_count` для разметки. При добавлении других типов задач (валидация, классификация, поиск объектов) понадобятся аналогичные поля — `validation_limit`/`validation_count` и т.д.
- **Тип-зависимая фильтрация в `/next`**: когда `can_label = TRUE`, выдавать задачи с `type='annotation'`; когда `can_validate = TRUE` — с `type='validation'`. Сейчас все задачи имеют один тип.
- **Авто-переход к валидации**: когда пользователь исчерпал лимит разметки, автоматически или вручную переключать его на валидацию. Нужен UI и логика на бэке.
- **Пакетное управление доступом**: выдать доступ к датасету сразу нескольким пользователям одним запросом.
- **Аудит изменений лимитов**: логировать, кто и когда менял лимиты конкретному пользователю.

## Датасеты

- **Статус `completed` для датасета**: автоматически переводить датасет в completed, когда все задачи достигли кворума.

- **Эндпоинт статистики**: `GET /datasets/{id}/stats` — admin-only, вычисляется одним запросом через агрегаты, не требует денормализации. Сюда уместно вынести глобальный прогресс, который сейчас нигде не возвращается:
  ```json
  {
    "tasks_total": 100,
    "tasks_pending": 43,
    "tasks_completed": 57,
    "tasks_with_any_answer": 72,
    "active_assignments": 5,
    "total_labels": 180,
    "total_participants": 34,
    "avg_labels_per_task": 1.8
  }
  ```

- **`DELETE /datasets/{id}`**: удаление датасета целиком не реализовано. Каскадно удалит все задачи, ассайнменты, лейблы и записи доступа — по аналогии с `DELETE /tasks/{id}`, но без нужды корректировать счётчики (всё и так удаляется).

## Задачи (Tasks)

- **Тип `validation`**: логика выдачи задач-валидаций (проверка чужой разметки). Нужны отдельная страница и компонент аннотатора в режиме "только просмотр + вердикт". На бэке: новое значение в `TaskType` enum + миграция, логика в `GET /datasets/{id}/next` с учётом флага `can_validate`, хранение ссылки на проверяемый `label_id` в `task.task_metadata`.

- **Тип `classification`**: задача "есть ли что-то на картинке" — бинарный выбор, без рисования рамок.

- **Проактивное истечение ассайнментов**: фоновый job (Celery beat / APScheduler), который периодически переводит просроченные `in_progress` ассайнменты в `expired` и декрементирует `task.active_assignments`. Сейчас `expires_at` хранится, но обрабатывается только лениво — в момент попытки сабмита. Из-за этого `active_assignments` стейлится, если пользователь ушёл, не сабмитив. SQL для job:
  ```sql
  UPDATE tasks t
  SET active_assignments = active_assignments - sub.cnt
  FROM (
      SELECT task_id, COUNT(*) AS cnt
      FROM assignments
      WHERE status = 'in_progress' AND expires_at < NOW()
      GROUP BY task_id
  ) sub
  WHERE t.id = sub.task_id;

  UPDATE assignments
  SET status = 'expired'
  WHERE status = 'in_progress' AND expires_at < NOW();
  ```
  После внедрения ленивую проверку в `submit_label` можно убрать.

## Администрирование

- **Дашборд прогресса**: сколько каждый пользователь сделал задач в каждом датасете, какой процент выполнен.

- **Отклонение разметки (rejection flow)**: `PATCH /labels/{id}/status` → `rejected` уже работает, но не корректирует счётчики. Полноценный flow зависит от бизнес-логики:
  - Если `rejected` = "работа не засчитана, пользователь делает другую задачу" → декрементировать `access.labeled_count`, `task.completed_answers`, вернуть задачу в `pending`. Переоткрыть ассайнмент (обновить `status` и `expires_at`) для переразметки — новый создать нельзя из-за `UNIQUE (task_id, user_id)`.
  - Если `rejected` = "зафиксировали брак, квота всё равно сгорает" → текущее поведение корректно, ничего менять не нужно.

- **Нереализованные фильтры**: параметры объявлены в эндпоинтах, но логика не подключена:

  | Эндпоинт | Параметры |
  |---|---|
  | `GET /datasets/` | `search`, `status`, `owner_search`, `tag_ids` |
  | `GET /users/` | `search` |
  | `GET /tags/` | `search` |

## Источники данных (`/sources/`)

`GET /sources/` — заглушка, возвращает пустой список. Задумывался для настройки внешних хранилищ (S3, MinIO, Яндекс Object Storage), откуда фронтенд напрямую загружает контент задач, не проксируя через основной сервер. При реализации нужна модель `Source` в БД (тип хранилища, credentials/endpoint, bucket) и UI в панели администратора.
